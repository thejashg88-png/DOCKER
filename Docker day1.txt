1. Why does a Java developer need Docker?

Normally, to run a Spring Boot application, your machine needs things like:

Java 17/21
Maven/Gradle
Application dependencies
PostgreSQL/MySQL
Redis
Kafka
Environment variables

For example:

java -jar myapp.jar

But your colleague might have Java 17 while you have Java 21.

Or your application might require PostgreSQL, but they don't have PostgreSQL installed.

Docker solves much of this environment problem.

Instead of:

Developer machine
 ├── Java
 ├── Maven
 ├── PostgreSQL
 ├── Redis
 └── Application

you can eventually have:

Docker
 ├── Java/Spring Boot container
 ├── PostgreSQL container
 └── Redis container
 
 
 
2. Image vs Container — Java analogy

This is the most important concept.

Think of a Docker image like a packaged Java application environment.

Docker Image
   │
   ├── JRE/JDK
   ├── Application JAR
   ├── Libraries
   └── Configuration

Then:

Docker Image
      ↓
Docker Container
      ↓
Spring Boot application running

A useful analogy is:

Java
Class       → Object


Docker
Image       → Container



3. Let's use a Spring Boot example

Suppose your project produces:

target/
   └── payment-service.jar

Normally you run:

java -jar target/payment-service.jar

With Docker, eventually you'll be able to do:

docker run payment-service

And Docker will run your Spring Boot application inside a container.




4. Your first Docker command

You should still start with:

docker run hello-world

This isn't a Java application. It's simply a test to verify that Docker works.

Understand the flow:

docker run hello-world
          ↓
Docker looks for hello-world image
          ↓
If unavailable locally
          ↓
Pull image from Docker Hub
          ↓
Create container
          ↓
Start container
          ↓
Print message
          ↓
Container exits




5. Now think about Java

Suppose Docker has a Java image:

eclipse-temurin:21

This provides a Java 21 runtime environment.

You could conceptually have:

eclipse-temurin:21

       Container

      Java 21

For example, you may encounter:

eclipse-temurin:17
eclipse-temurin:21

The important thing isn't memorizing the names yet.

Understand:

A Docker image can provide the Java runtime your application needs.

Docker Day 1 — Core Concepts & Commands

First remember this simple relationship:

Docker Hub
    ↓
  Image
    ↓
Container
    ↓
Your application runs
1. Docker Image
Definition

A Docker image is a packaged/template version of an application that contains everything needed to create a container.

For example, imagine you have a Spring Boot application:

Spring Boot Application
        +
Java Runtime
        +
Application JAR
        +
Configuration
        ↓
     Docker Image

You can think of an image as a blueprint.

It doesn't normally "run" by itself. A container is created from it.

Example
docker images

This displays the images available on your computer.

You might see:

REPOSITORY    TAG       IMAGE ID       SIZE
hello-world   latest    4f55086f7dd0   10kB
2. Container
Definition

A container is a running or stopped instance created from a Docker image.

Think:

Image = Blueprint
Container = Actual running instance

For Java:

springboot-image
       ↓
   Container
       ↓
Spring Boot application

You can create multiple containers from the same image:

        Spring Boot Image
          /          \
         ↓            ↓
    Container 1   Container 2

For example:

my-spring-app:1.0
       ↓
   Container A
       ↓
localhost:8080

and:

my-spring-app:1.0
       ↓
   Container B
       ↓
localhost:8081

Both containers can come from the same image.

3. Docker Hub
Definition

Docker Hub is a public registry where Docker images are stored and shared.

Think of it somewhat like a central repository for Docker images.

For example, Docker Hub contains images for:

Ubuntu
PostgreSQL
MySQL
Redis
Nginx
Java
Node

When you ran:

docker run hello-world

Docker didn't find hello-world locally.

So it did:

Your Computer
     ↓
"Do I have hello-world?"
     ↓
     No
     ↓
Docker Hub
     ↓
Download hello-world image
     ↓
Create container

That's why you saw:

Unable to find image 'hello-world:latest' locally

Then:

Pulling from library/hello-world
4. docker run
Definition

docker run creates a new container from an image and starts it.

Syntax:

docker run IMAGE_NAME

Example:

docker run hello-world

Docker essentially does:

Find image
    ↓
If not available locally → download it
    ↓
Create container
    ↓
Start container
Java example

Later, suppose you create:

my-spring-app:1.0

You could run:

docker run my-spring-app:1.0

Your Spring Boot application would start inside the container.

5. docker ps
Definition

docker ps shows currently running containers.

Run:

docker ps

Example:

CONTAINER ID   IMAGE          STATUS        PORTS
abc123         my-spring-app  Up 2 minutes  0.0.0.0:8080->8080/tcp

Important information:

Column	Meaning
CONTAINER ID	Unique ID of container
IMAGE	Image used to create it
STATUS	Whether it is running
PORTS	Port mappings
NAMES	Container name
Important

docker ps shows only running containers.

If you want running + stopped containers:

docker ps -a

Your hello-world container will probably appear there because it finished execution.

6. docker stop
Definition

docker stop stops a running container.

Syntax:

docker stop CONTAINER_ID

For example:

docker stop abc123

Or if you give the container a name:

docker stop my-spring-app
Java example

Suppose your Spring Boot application is running:

Spring Boot
     ↓
Container
     ↓
Port 8080

You run:

docker stop my-spring-app

The application stops.

The image is not deleted.

The container is stopped, but it still exists.

You can see it with:

docker ps -a
Very Important Difference

This is the part I want you to remember as a Java developer:

IMAGE
  │
  │ docker run
  ↓
CONTAINER
  │
  │ application starts
  ↓
RUNNING CONTAINER
  │
  │ docker stop
  ↓
STOPPED CONTAINER

The image remains.

For example:

Image
my-spring-app:1.0
       │
       ├──── Container A → stopped
       │
       └──── Container B → running
The 6 Things to Remember
Concept / Command	Simple meaning
Image	Blueprint/package for your application
Container	Instance created from an image
Docker Hub	Online registry for Docker images
docker run	Create + start a container
docker ps	Show running containers
docker stop	Stop a running container
The most important mental model

If you're coming from Java:

Docker Image ≈ packaged application template
Container ≈ running instance
Docker Hub ≈ remote image registry

And the basic commands:

docker images       :: What images do I have?
docker run          :: Create and start a container
docker ps           :: What containers are running?
docker ps -a        :: What containers exist?
docker stop         :: Stop a container

One correction to that last analogy: an image is not exactly the same as a JAR. A JAR is an application artifact, while a Docker image can contain the application 
plus its runtime and OS-level filesystem/dependencies. This distinction will become very important when we create your first Spring Boot Docker image.


docker rm
Definition

docker rm removes/deletes a Docker container.

docker rm CONTAINER_ID

For example:

docker rm abc123

This removes the container with ID abc123.

Important distinction

docker rm removes a container, NOT an image.

Image
  ↓ docker run
Container
  ↓ docker rm
Container deleted

The image is still there.

Example with your hello-world

You can see your container:

docker ps -a

You might see:

CONTAINER ID   IMAGE         STATUS
abc123         hello-world   Exited (0)

Remove it:

docker rm abc123

Then:

docker ps -a

The container will be gone.

But:

docker images

will still show:

hello-world

because the image wasn't deleted.

What if the container is running?

Normally:

docker rm abc123

will not remove a running container.

You should first:

docker stop abc123
docker rm abc123

There is also:

docker rm -f abc123

which force-removes a running container.

For now, as a beginner, prefer:

docker stop
docker rm
2. docker pull
Definition

docker pull downloads a Docker image from a registry, usually Docker Hub, to your local computer.

Syntax:

docker pull IMAGE_NAME

Example:

docker pull nginx

Docker will download the nginx image.

You can then check:

docker images

You might see:

REPOSITORY   TAG       IMAGE ID
nginx        latest    xxxxxxxx
What happens?
Docker Hub
    │
    │ docker pull nginx
    ↓
Your Computer
    │
    ↓
nginx Image

Important: docker pull only downloads the image. It does not create or start a container.

docker pull vs docker run

This is very important.

docker pull
docker pull nginx

Means:

"Download the nginx image to my computer."

Nothing is running yet.

docker run
docker run nginx

Means:

"Give me a container created from the nginx image and start it."

If the image doesn't exist locally, docker run will generally pull it automatically first.

So:

docker run nginx

can effectively result in:

Is nginx image local?
       ↓
      No
       ↓
Pull image
       ↓
Create container
       ↓
Start container
docker rm vs docker rmi

You'll encounter another command soon:

docker rmi

Don't confuse them:

Command	Removes
docker rm	🟦 Container
docker rmi	🟩 Image
docker stop	Stops container
docker pull	Downloads image
docker run	Creates + starts container

Think of it this way:

              IMAGE
                │
          docker pull
                ↑
            Docker Hub
                │
                │ docker run
                ↓
            CONTAINER
                │
          docker stop
                ↓
        STOPPED CONTAINER
                │
           docker rm
                ↓
        CONTAINER DELETED
One-line memory trick

pull = bring image in

rm = remove container

rmi = remove image

For your Docker Day 1, these are the core commands you've now covered:

docker images
docker pull
docker run
docker ps
docker ps -a
docker stop
docker rm

The next useful command is docker exec, because that's how you'll enter a running container and inspect what is happening inside it.





Real time example of using the docker



Yes. Since you already have the JAR file of your Java application, this is the perfect next Docker exercise.

We'll do it in the simplest possible way:

Your Java JAR
     ↓
Dockerfile
     ↓
Docker Image
     ↓
Docker Container
     ↓
Spring Boot application
1. Create a folder

For example:

C:\docker\search-pg

Put your JAR inside it:

C:\docker\search-pg
│
├── search-pg.jar
└── Dockerfile

You can use your actual JAR filename instead of search-pg.jar.

2. Create a Dockerfile

Inside the same folder, create a file named exactly:

Dockerfile

No .txt extension.

Put this inside:

FROM eclipse-temurin:17-jre


WORKDIR /app


COPY search-pg.jar app.jar


EXPOSE 8080


ENTRYPOINT ["java", "-jar", "app.jar"]
What each line means
FROM
FROM eclipse-temurin:26-jre

This tells Docker:

Start with a Java 26 runtime image.

If your application uses Java 8, 11, 17, 21, etc., we should use the corresponding runtime.

You can check your application's Java version with:

java -version

If your JAR was built with Java 17, the above is appropriate.

WORKDIR
WORKDIR /app

Creates/uses /app as the working directory inside the container.

So inside the container we'll have:

/app
   └── app.jar
COPY
COPY search-pg.jar app.jar

Copies your JAR from your Windows folder into the Docker image.

Windows
search-pg.jar
     ↓
Docker Image
/app/app.jar
EXPOSE
EXPOSE 8080

This documents that the application uses port 8080.

Important: EXPOSE by itself does not make the application accessible from your Windows machine. We'll map the port when running the container.

ENTRYPOINT
ENTRYPOINT ["java", "-jar", "app.jar"]

This tells Docker what to execute when the container starts.

It's essentially:

java -jar app.jar

inside the container.

3. Build the Docker image

Open CMD in your project folder:

cd C:\docker\search-pg

Then:

docker build -t search-pg:1.0 .

The . at the end is important.

It means:

Use the current folder as the build context.

After successful build:

docker images

You should see something like:

REPOSITORY   TAG    IMAGE ID
search-pg    1.0    xxxxxxxx

You have now converted:

search-pg.jar
      ↓
Docker image
search-pg:1.0
4. Run your application

Now:

docker run -p 8080:8085 search-pg:1.0

The mapping:

-p 8080:8080
   ↑      ↑
   │      └── Container port
   └───────── Windows host port

So:

Windows
localhost:8080
      ↓
Docker
      ↓
Container
      ↓
Java application
      ↓
8080

If your Spring Boot application starts successfully, you'll see its normal startup logs.

For example:

Started SearchPgApplication in 4.123 seconds
5. Check the container

Open another CMD window:

docker ps

You should see:

CONTAINER ID   IMAGE          STATUS          PORTS
abc123         search-pg:1.0  Up 20 seconds   0.0.0.0:8080->8080/tcp

This means your Java application is running inside Docker. 🎉

6. Test your API

If your application has an endpoint such as:

GET /search

you can access:

http://localhost:8080/search

Or test it using Postman.

One important thing about your "search PG" application

I'm assuming PG means PostgreSQL.

If your Java application connects to PostgreSQL, there is one additional issue.

For example, your application might currently have:

spring.datasource.url=jdbc:postgresql://localhost:5432/searchdb
spring.datasource.username=postgres
spring.datasource.password=password

⚠️ This will usually not work as-is inside Docker.

Why?

Inside a Docker container:

localhost

means the Java container itself, not your Windows machine and not another PostgreSQL container.

Eventually we'll change this to something like:

spring.datasource.url=jdbc:postgresql://postgres:5432/searchdb

and run:

┌───────────────────────────────┐
│ Docker                        │
│                               │
│  ┌─────────────┐              │
│  │ Spring Boot │              │
│  │ Container   │              │
│  └──────┬──────┘              │
│         │                     │
│         │ postgres:5432       │
│         ↓                     │
│  ┌─────────────┐              │
│  │ PostgreSQL  │              │
│  │ Container   │              │
│  └─────────────┘              │
│                               │
└───────────────────────────────┘

We'll use Docker Compose for that, which is the proper next step for a Java backend application with PostgreSQL.
